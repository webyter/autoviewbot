# Production Runbook

Everything you need to run AutoViewer unattended. For day-to-day commands see
[`OPERATIONS.md`](./OPERATIONS.md).

## 1. Requirements

- Node.js **>= 20** (the app is tested on 20 and 22)
- A persistent disk for `SESSION_DIR` (WhatsApp credentials + user DB)
- Linux with systemd (recommended) or Docker

## 2. Install

```bash
git clone https://github.com/webyter/autoviewbot && cd autoviewbot
npm ci --omit=dev            # or: npm install --omit=dev
cp .env.example .env         # then edit .env
mkdir -p session
```

**No key is shipped with the code.** Set your own Groq key to enable ChatAI
and voice-note transcription:

```bash
GROQ_API_KEY=gsk_your_key_here
```

Resolution order (covered by `test/groq-key.js`):
1. `GROQ_API_KEY` in the environment
2. `GROQ_API_KEY` in `config.env` / `.env` (or the files in `CONFIG_ENV_FILES`)

An empty or whitespace-only value counts as "not set" — without a key the AI
features stay off and say so instead of failing silently.

## 3. Configure `.env`

| Variable | Required? | Notes |
| --- | --- | --- |
| `SESSION_SECRET` | recommended | `openssl rand -hex 32`. Unset ⇒ a secret is generated and persisted to `SESSION_DIR/.session_secret`. |
| `GROQ_API_KEY` | for ChatAI | Your own Groq key. Without it, ChatAI and transcription stay off. |
| `GROQ_MODEL` | no | Default `openai/gpt-oss-120b`; falls back automatically. |
| `PORT` | no | Default `3000`. |
| `NODE_ENV` | no | `production` in real deployments. |
| `PUBLIC_URL` | recommended | Public base URL for invite links + keep-alive ping. |
| `COOKIE_SECURE` | if plain HTTP | `false` when the dashboard is served over plain HTTP, `true` behind TLS. Unset ⇒ secure when `NODE_ENV=production`. |
| `TRUST_PROXY` | yes, behind a proxy | Number of proxy hops to trust (`0` when directly exposed). |
| `MAX_INSTANCES` | no | Concurrent bot limit (also in the admin panel). |
| `SESSION_DIR` | no | Default `./session` — **must be on a persistent disk**. |
| `ADMIN_USERNAMES` | no | Comma-separated usernames promoted to platform admin. |
| `INVITE_CODE` | no | Comma-separated registration codes (admin panel codes work too). |
| `ADMIN_CONTACT` | no | WhatsApp number shown on the login page. |

## 4. Run it

### systemd (recommended)

```bash
sudo cp deploy/autoviewer.service /etc/systemd/system/autoviewer.service
sudo systemctl daemon-reload
sudo systemctl enable --now autoviewer.service
sudo systemctl status autoviewer.service
```

The shipped unit is already hardened: `NoNewPrivileges`, `ProtectSystem=strict`,
`ProtectHome=read-only`, a writable path limited to `session/`, `PrivateTmp`,
`PrivateDevices`, `SystemCallFilter=@system-service`, plus
`Restart=always` / `RestartSec=5`.

> **Adjust `User=`/`Group=`/`WorkingDirectory=`/`ReadWritePaths=`** to match
> where you installed the app, and set `COOKIE_SECURE=false` if you serve the
> dashboard over plain HTTP (a secure cookie is silently dropped over HTTP and
> every login would bounce back to `/login`).

### Render blueprint (auto-generated)

`render.yaml` is generated by the app itself, so the deployed config can never
drift from what the code needs:

```bash
npm run render:init                      # regenerate from .env + the current file
npm run render:init -- --plan starter --name my-bot --public-url https://my-bot.onrender.com
git add render.yaml && git commit -m "chore: update render blueprint"
```

The generator:
- preserves hand-made choices (service name, plan, region, admin contact),
- writes every required key (node version, `NODE_ENV`, `COOKIE_SECURE=true`,
  `TRUST_PROXY=1`, `KEEPALIVE_INTERVAL_MIN`, `PUBLIC_URL`, health path,
  reproducible build/start commands, `autoDeploy`),
- **never writes secrets** — the Groq key, session secret and invite codes are
  emitted as `sync: false` placeholders for the Render dashboard,
- quotes values YAML would otherwise misread (a version like `20.18.0`, a
  phone number that would become an int, `true`, `on`, …).

On Render the app also refreshes the blueprint at startup with the public URL
the platform reports, and logs that the file is ephemeral there — run
`npm run render:init` locally and commit it to keep them in sync.

### Docker

```bash
docker build -t autoviewer .
docker run -d --name autoviewer \
  -p 3000:8080 \
  -v autoviewer-data:/app/session \
  -e PUBLIC_URL=https://bot.example.com \
  -e SESSION_SECRET="$(openssl rand -hex 32)" \
  --restart unless-stopped \
  autoviewer
```

Put a TLS-terminating reverse proxy (Caddy/nginx) in front of it and forward
`X-Forwarded-Proto` / `X-Forwarded-For`.

## 5. First run

1. Open `https://your-host/` and register — the **first account becomes the
   platform admin**.
2. Link the WhatsApp account: scan the QR on the dashboard.
3. In the admin panel create invite codes for your users.

## 5b. Render (free tier)

The app detects Render automatically (`RENDER` / `RENDER_EXTERNAL_URL`) and
**keeps itself awake** by requesting its own public URL every ~9 minutes —
Render spins a Free web service down after 15 minutes without inbound
traffic, and a request that leaves the instance and comes back through
Render's edge counts as inbound traffic.

Nothing to configure: `render.yaml` is ready to use. Optional knobs:

| Variable | Default | Purpose |
| --- | --- | --- |
| `PUBLIC_URL` | – | Your service URL (`https://<service>.onrender.com`). Not required for keep-alive (the platform URL is auto-detected) but it fixes the invite links. |
| `KEEPALIVE_URL` | – | Override the URL that gets pinged. |
| `KEEPALIVE_INTERVAL_MIN` | `9` | Ping interval in minutes (clamped to 2-14). |

**Self-ping prevents sleep; it cannot wake a sleeping service.** After a
redeploy the first visitor still pays Render's ~1 minute cold start. Add the
external layer for that — the repo ships `.github/workflows/keep-alive.yml`,
a GitHub Actions cron that pings `https://<service>/health` every 10 minutes
from the outside:

1. Repo -> **Settings -> Secrets and variables -> Actions** -> add the secret
   `SELF_URL = https://<service>.onrender.com`
2. The workflow runs on its schedule (and can be triggered manually).

Render's own docs recommend an external uptime monitor (UptimeRobot,
cron-job.org) for exactly this reason — add one for real redundancy.

### Render Free has an EPHEMERAL filesystem

Every spin-down, restart or redeploy **wipes the local disk**: the WhatsApp
sessions and the user database (`session/users.json`) are lost and users have
to re-scan the QR. Keep-alive reduces how often that happens but cannot
prevent a redeploy from resetting it.

For anything real on Render:
- attach a **persistent disk** (paid) and point `SESSION_DIR` at the mount
  path (e.g. `/opt/render/project/src/session`), or
- run the bot on a VPS (see `deploy/autoviewer.service`) and keep Render for
  the dashboard only, or
- accept the re-linking and let users re-scan.

The app logs a warning at startup when it detects Render so this is never a
surprise.

## 6. Operations

| Task | Command |
| --- | --- |
| Status / logs | `systemctl status autoviewer` · `journalctl -u autoviewer -f` |
| Restart | `sudo systemctl restart autoviewer` |
| Backup | `scripts/backup.sh /var/backups/autoviewer` |
| Restore | stop service → unpack archive → start service |
| Health probe | `GET /health` → `{"status":"ok",...}` |

`scripts/backup.sh` copies the user DB, invite store, session secret and each
user's WhatsApp credentials into a `0600` tarball. **Treat those archives as
credentials.**

### Health & monitoring

`GET /health` returns uptime, active bots, memory and the AI status — usable
as a load-balancer probe and a monitoring check:

```bash
curl -fsS https://your-host/health | jq .
```

Alerts worth having:
- service not `active` (`systemctl is-active autoviewer`)
- `/health` not returning 200
- `activeBots` stuck at 0 while accounts should be running
- journal errors matching `crashed` / `restart counter` growing

## 7. Hardening checklist

- [ ] `SESSION_SECRET` set explicitly and stored outside the repo
- [ ] `GROQ_API_KEY` set to your own key (no key is shipped with the code)
- [ ] TLS in front of the dashboard + `COOKIE_SECURE=true`
- [ ] `TRUST_PROXY` set to the real number of proxy hops
- [ ] `PUBLIC_URL` set (otherwise invite links use the request host)
- [ ] `ADMIN_USERNAMES` set; `INVITE_CODE` managed in the admin panel
- [ ] `session/` on a persistent, backed-up disk with `0600` permissions
- [ ] Registration closed (no `INVITE_CODE` and no admin codes) unless wanted
- [ ] Log retention configured in journald (`journalctl --vacuum-time=14d`)
- [ ] Backups scheduled (cron → `scripts/backup.sh`) and a restore rehearsed
- [ ] `npm audit --production` clean after dependency updates

## 8. Upgrades

```bash
cd /path/to/autoviewbot
scripts/backup.sh /var/backups/autoviewer
git pull && npm ci --omit=dev
sudo systemctl restart autoviewer
curl -fsS https://your-host/health
```

The WhatsApp session survives upgrades — it lives in `SESSION_DIR`, not in the
code.

## 9. Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| Dashboard logs out immediately | `secure` cookie over plain HTTP → set `COOKIE_SECURE=false`, or serve over HTTPS. |
| "Another autoviewer instance is already running" | A second manager is alive. `pgrep -af autoviewer` and stop the stray one — the lock file is `session/autoviewer.lock`. |
| Bot shows `stopped` | The account was logged out; open the dashboard and re-scan the QR. |
| ChatAI replies with an error | Wrong model for your key → set `GROQ_MODEL` (e.g. `openai/gpt-oss-120b`) or check `GET /api/groq-test`. |
| Service restarts in a loop | `journalctl -u autoviewer -n 50` — a code crash no longer wipes sessions, so the account stays linked. |
| `.vv` says "Media not available" | The media expired or the sender's device is offline; the bot asks the sender to re-upload, which only works while their phone is online. |
